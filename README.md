# Netmap Pinger

Веб-карта сети с импортом из Friendly Pinger: узлы, исходная геометрия линий, любое количество IP и DNS-имён
на узел, непрерывный ICMP-опрос независимо от браузера. IPv4/IPv6 и IDNA поддерживаются.
Число адресов у узла не имеет фиксированного ограничения; общий JSON-запрос/файл ограничен
16 МБ для защиты процесса и браузера от чрезмерного объёма данных.
Узел зелёный при ответе всех адресов, жёлтый при ответе части, красный только при подтверждённом
отсутствии ответа всех адресов. Ошибка DNS/запуска ping, отсутствие замера, пауза и устаревшие
данные имеют отдельные состояния. Линии отражают топологию, а не измерение физического канала.

В классическом виде под каждым узлом есть отдельная точка для каждого IP и DNS-имени. Подсказка показывает
адрес и его состояние; нажатие открывает историю именно этого адреса. Полные подписи и результаты
доступны также в боковой панели. Число точек равно числу адресов узла, без фиксированных слотов.

## Виды карты

В шапке переключатель «Карта / Схема». «Карта» показывает компактные значки в стиле Friendly Pinger.
В «Схеме» на полотне отображаются сетевые условные обозначения, например цилиндр с четырьмя
стрелками для маршрутизатора, коммутатор со встречными стрелками и облако для внешней сети.
Обозначение задаётся полем «Тип устройства». Под символом подписаны узел, его IP и DNS-имена
со статусами и метками каналов. Нажатие на адрес открывает его историю. Длинный адрес и комментарий
можно прочитать в подсказке и карточке узла.

Схема использует сохранённые координаты как исходные позиции и раздвигает символы с подписями
при наложении. Это происходит только при отображении. Ручное добавление, редактирование и перемещение
узлов работают в обоих видах. Концы связей следуют за символами, изгибы подстраиваются под смещение.
Связи со свободными концами показаны пунктиром с кружком на свободном конце. Выбранный вид
запоминается в браузере.

## Статистика ICMP

«Статистика» под картой открывает графики всех узлов. В карточке узла есть «Статистика» по всем
его адресам и «График» у каждого адреса. Периоды — 3 часа, сутки, неделя, месяц (30 дней) и год
(365 дней). График показывает медиану RTT, диапазон минимум–максимум и долю потерь по интервалам.
В сводке видны также средняя RTT, P95, стандартное отклонение, число ответов, отправленных пакетов и ошибок
опроса. Стрелки на графике выбирают интервал и показывают его замеры. Время указано в МСК.

Netmap использует результаты своего обычного опроса. Потери считаются по подтверждённым ICMP-ответам
и тайм-аутам, ошибки DNS и запуска показаны отдельно. Пустые интервалы означают пропуски измерений.
Агрегаты SQLite хранятся с шагом 5 минут, час и сутки. Для месяца график объединяет данные по два
часа. Первый интервал округляется к началу корзины. Медиана и P95 приближённые, из гистограммы RTT.
Netmap накапливает статистику с первого собственного измерения.

Узел имеет метку «Площадка», а каждый его адрес — метку «Канал». В статистике можно сочетать
фильтры. Например, «Внешний (WAN)» без выбора площадки покажет WAN по всем объектам. Метки
редактируются в карточке узла и сохраняются в JSON-копии. Заполнить метки на базе текущей карты можно
из YAML-инвентаря и файла `Targets` SmokePing:

```powershell
python -m netmap.labels --network <network.yaml> --map <export.json> --smokeping-targets <Targets> --output <labeled.json> --report <report.json>
```

Команда дополняет пустые метки и выдаёт список целей SmokePing, отсутствующих в карте. Она использует
группы ICMP-проб FPing, включая Sites, VPN, LAN, WAN и Internet. У DNS-проб свой протокол и интервалы.
Перед применением проверьте отчёт и загрузите подготовленную копию через предпросмотр с актуальной
ревизией. Адреса, связи и параметры опроса сохраняются.

## История

Кнопка «История обрывов» открывает события всех узлов; кнопка в карточке или точка адреса —
историю выбранного узла/IP/имени. Есть фильтры по периоду в МСК, узлу, адресу и уровню
(весь узел или отдельные адреса), временная шкала и постраничная загрузка.

История хранится в той же локальной SQLite: интервалы состояний, первая/последняя проверка,
переходы в down/up/partial/error. Успешные одинаковые проверки обновляют последний замер
интервала, а не добавляют миллионы одинаковых строк. Записи не удаляются автоматически.
Пауза мониторинга, удаление адреса и переименование узла не стирают старые события.

История начинается с первого измерения новой версией: прошлые обрывы не восстанавливаются
из текущего состояния. Первоначальный down помечен как наблюдаемый с первого замера,
его фактическое начало неизвестно. После длительного перерыва сборщика пишется gap;
он не считается сетевым обрывом. При устаревшем открытом событии его длительность ограничена
последним замером. Начало/восстановление — время первой соответствующей проверки, точность
определяется периодом опроса. Ошибка DNS показана отдельно от подтверждённого отсутствия ICMP.
Таблица показывает границы и полную длительность наблюдаемого состояния. Шкала показывает часть,
попавшую в выбранный период. Смена IP в DNS или причины ответа внутри одного состояния сохраняется
со временем замера. Для старых записей доступна сохранившаяся деталь из прежней версии сборщика.

## Дополнение адресов из реестра

`python -m netmap.inventory --network <network.yaml> --map <export.json> --dns <dns.json>
--output <enriched.json> --report <report.json>` дополняет существующие узлы. Нужен PyYAML
из requirements. Файл DNS содержит имя → список IP, разрешённых с сервера мониторинга;
PTR-имена добавляются после подтверждения прямой DNS-записью.

Идентичность устанавливается по основному адресу и объявленным интерфейсам. Адреса шлюзов,
DNS-серверов и peer-стороны VPN не считаются адресами устройства. Общие адреса изолированных
bridge-сетей и неоднозначные соответствия остаются в отчёте; имена чужого веб-фронтенда
не приписываются backend-узлу. Существующие значения сохраняются; подтверждённые ошибки
исправляются отдельно после сверки с живым устройством. Данные карты и отчёт — в gitignored
`var/`.
Новые DNS-имена с несколькими возможными владельцами включаются в `ambiguous_dns`.

## Локальный запуск

Из корня репозитория с Python 3.11 или новее:

```powershell
python -m pip install -r netmap/requirements.txt
python -m netmap.app --port 55474
```

Открыть http://127.0.0.1:55474/. Зависимости — `netmap/requirements.txt`.
Если выбранный порт занят/зарезервирован Windows, `--port 0` выбирает свободный порт и печатает URL.
БД по умолчанию — `var/netmap.sqlite` (gitignored, локальный диск).
Один процесс/worker: иначе каждый worker запускает свой сборщик. Reload в production не применять.

Импорт подготовленного экспорта Friendly Pinger без секретов только в новую пустую БД:

```powershell
python -m netmap.import_friendly var/friendly-source.json --db var/netmap.sqlite
```

Экспорт содержит исходную .map в base64 (CP1251), безопасные секции Config/Device/LineType,
размеры GIF и описание источника. Вложенные `[Name]` и строковые имена читаются отдельно.
Оригинальные полилинии сохраняются при импорте. На карте привязанные концы линий всегда идут
к центрам узлов; промежуточные изгибы и свободные концы сохраняют свои координаты.
Привязка концов к прямоугольникам исходных иконок
при неоднозначности не угадывается: линия остаётся с координатами, замечание видно в настройках.

Редактор сохраняет координаты, адреса, узлы, связи и период/тайм-аут опроса. Изменения из двух
окон защищены ревизией: устаревшая запись отклоняется без перезаписи. Скачать/загрузить JSON-копию
можно в панели узлов. При замене карты сначала скачать текущую копию.
Внешние команды Friendly Pinger (RDP, PowerShell, выключение и т. п.) не выполняются веб-сервером.

Кнопка «Дублировать» в карточке узла открывает новую копию в редакторе: название с пометкой
«(копия)», тип, адреса в исходном порядке, комментарии, заметки и настройки мониторинга уже заполнены.
Перед сохранением их можно изменить; «Отмена» ничего не создаёт. Копия появляется рядом с исходным
узлом, с отдельным идентификатором и собственной историей. Связи остаются у исходного узла.

Шапка на большом экране — 24 px; управление масштабом, перемещением узлов и связями находится
в ней. Состояние последнего цикла, длительность, число адресов и период — в нижней статусной панели.
Кнопка «Узлы» сворачивает список и на большом экране. «Вся карта» подгоняет масштаб под выбранный вид.
Ручное масштабирование/перемещение отключает
автоматическую подгонку до следующего «Вся карта»; на узком экране кнопки шапки переносятся.
В режиме «Двигать узлы» выберите узел на карте или в списке: стрелки сдвигают его на 1 единицу
координат, Shift + стрелки — на 10. Координаты и привязанные концы линий сохраняются автоматически;
повторные нажатия во время сохранения объединяются. В полях ввода и диалогах стрелки работают обычно.
Для переноса группы добавляйте/убирайте узлы через Ctrl/⌘ или Shift + клик, либо выделите их
рамкой с Shift на пустом месте карты. Кнопка «Выделить группу» позволяет выбирать узлы нажатием
и рамкой без клавиатуры, в том числе на сенсорном экране. Потяните любой выделенный узел или
нажмите стрелку: вся группа переместится на одинаковое расстояние и сохранится одним изменением.
Внутренние связи перемещаются целиком вместе с изгибами; у внешних связей двигается только
привязанный конец. Esc или клик по пустому месту снимает выделение. Без режима выделения
перетаскивание пустого места перемещает карту. Рамка выбирает центры узлов, видимых по текущему фильтру.
На сенсорном экране масштаб меняется разведением/сведением двух пальцев вокруг точки между ними;
двумя пальцами можно одновременно перемещать карту. Жест работает и при касании узлов/связей.
Появление второго пальца отменяет незавершённое перетаскивание узла; масштабирование не меняет
сохранённые координаты и не открывает карточки. Одним пальцем можно продолжить перемещение карты.

Каждый адрес редактируется отдельной парой полей «IP-адрес или DNS-имя» / «Комментарий».
Стрелки ↑ и ↓ перемещают адрес вместе с комментарием; порядок сохраняется, первый адрес — основной.
Напротив адреса в редакторе показано текущее состояние фонового опроса; время, задержка и детали —
в подсказке. Состояния обновляются при открытом редакторе, новые адреса показываются без данных до сохранения и опроса.

Отметка **«Допускается недоступность»** (`allow_offline`, по умолчанию выключена) предназначена для
планово выключаемых и переносимых устройств. Полностью доступный узел зелёный, остальные состояния
такого узла и его неотвечающих адресов — серые. Пунктирная рамка и подпись в карточке обозначают отметку.
Узел исключается из «Требуют внимания» и красного/жёлтого счётчиков; фильтр «Непостоянные узлы»
показывает все отмеченные узлы. Опрос не отключается, реальные состояния и история не подменяются.
Фильтры отдельных состояний продолжают показывать фактическую доступность. Старые JSON-копии совместимы.
Комментарии хранятся в `address_comments` узла по нормализованному адресу, входят в экспорт,
поиск и подсказки точек; старые копии карты без этого поля совместимы. Удаление адреса удаляет
его текущий комментарий, история измерений сохраняется.

**Netwatch** включён по умолчанию у опрашиваемых узлов с обязательной доступностью, в том числе
после обновления старой карты. В редакторе его можно выключить отдельно для каждого узла.
В «Настройки → Настройки карты → Netwatch» задаются адрес получателя и задержка в целых минутах (по умолчанию 10). Если все адреса узла не отвечают
в течение заданного времени, Netwatch ставит письмо в очередь. Как только ответит хотя бы один
адрес, ставится письмо о восстановлении этого обрыва.
Отсчёт начинается с первого замера без ответов. Изменение задержки применяется на следующем
полном опросе к обрывам, для которых письмо ещё не поставлено в очередь. Ошибки проверки и
пропуски измерений прерывают подтверждение обрыва до постановки письма в очередь.
Состояние и очередь сохраняются в SQLite. Каждая попытка отправки использует текущий адрес
получателя. После сбоя SMTP служба повторяет отправку каждую минуту, сохраняя порядок писем.

Импорт JSON открывает сравнение с текущей ревизией. В нём видны новые, удаляемые и изменённые узлы
и связи, настройки опроса и адреса, которые перестанут опрашиваться. Импорт применяет только
показанную ревизию. При правке из другого окна выберите копию снова и проверьте новый список.

Для заполнения существующих адресов из реестра: `python -m netmap.comments --network <network.yaml>
--map <export.json> --output <commented.json> --report <report.json>`. Команда создаёт проверяемую
копию и отчёт, не добавляет/удаляет адреса и не перезаписывает непустые комментарии владельца.
Назначение берётся из интерфейсов, VPN и площадок; неизвестный интерфейс обозначается явно.
Применять копию через редактор/API с актуальной ревизией, не заменой рабочей SQLite.

У каждого адреса в карточке есть **Ping** и **Трассировка**. Команды выполняются на сервере
мониторинга с построчным выводом в окно диагностики; «Остановить» и закрытие окна завершают процесс.
Ping отправляет 10 пакетов, трассировка ограничена 20 переходами, любая команда — 45 секундами;
одновременно не более трёх команд для всех окон. Допускаются только адреса выбранного узла,
произвольные команды/параметры не принимаются. DNS разрешается в момент запуска команды.
Linux использует `ping` и `stdbuf -oL traceroute` (UDP, один запрос на переход, ожидание 1 с),
Windows — `ping.exe` / `tracert.exe`. Отсутствие ответов промежуточных маршрутизаторов само по себе
не доказывает обрыв. Ручные команды не меняют историю и результаты фонового опроса.

## Интеграция со сводкой watch

Ссылка «Карта и история» в инциденте передаёт `canonical` (может повторяться), `since` и `until`
в секундах эпохи. Карта выделяет только однозначно сопоставленные узлы и открывает историю
в том же интервале с точностью до секунды. Неизвестные объекты и общие адреса показываются явно.
Для интеграции разместите индекс `/watch/navigation.json` рядом с картой на том же origin;
карточка узла содержит обратные ссылки на эпизоды Check_*, Zabbix и MikroTik. В окне инцидента
показываются источники с пересекающимися эпизодами. Время открытого эпизода ограничено концом
наблюдений в выпуске. Старый суточный индекс доступен в обычной карточке узла.
Отсутствие связанной истории не подтверждает доступность, нарисованные линии не измеряют каналы.

## Размещение

Прямой запуск предназначен для локальной работы на loopback. Для общего доступа
используйте HTTPS и аутентификацию на обратном прокси. Ограничьте доступ к карте
и её API доверенными операторами: они могут менять список опрашиваемых адресов.

Примеры для Linux находятся в `netmap/deploy/`. Выберите свой домен и пути к TLS-сертификату
в `apache-vhost.conf`. Служба работает от учётной записи `netmap-pinger`, которую нужно создать
до включения службы. Разместите репозиторий и venv по пути из unit либо настройте
`WorkingDirectory` и `ExecStart`. Установите `ping`, `traceroute` и `htpasswd`.
Проверьте, что GID службы входит в диапазон ядра `net.ipv4.ping_group_range`.

1. Создайте файл bcrypt-паролей командой `htpasswd -Bc <файл> admin`. Apache должен иметь
   право его читать. Для смены пароля через карту процессу приложения нужны права на
   запись в каталог файла. Включите службы `netmap-pinger.service` и `netmap-pinger.socket`
   и проверьте `/api/health` через их Unix-сокет.
2. Подключите vhost, проверьте конфигурацию Apache и перезагрузите конфигурацию.
   Проверьте запрос пароля, страницу и API через HTTPS, затем завершение полного цикла ICMP.
   `apache-location.conf` пригодится для перенаправления прежнего URL `/netmap/`.
3. Держите рабочую SQLite на локальном диске. Перед обновлением снимайте согласованную
   резервную копию через SQLite Backup API. При переносе укажите существующий файл флагом
   `--db` и запускайте один сборщик, чтобы сохранить карту и накопленную историю.

Настройте `NETMAP_HOSTS` списком разрешённых имён через запятую. По умолчанию разрешены
`127.0.0.1` и `localhost`. `NETMAP_PASSWORD_FILE` указывает на файл bcrypt-паролей для
смены пароля из интерфейса. Доступ проверяет Apache, а для смены пароля приложение
дополнительно требует HTTPS, тот же Origin и действующий пароль.

Для Netwatch задайте `NETMAP_SMTP_HOST`, `NETMAP_SMTP_SENDER` и `NETMAP_SMTP_PASSWORD`
в окружении процесса. `NETMAP_SMTP_PORT` по умолчанию равен 587. Используются STARTTLS и
вход с адресом отправителя в качестве имени пользователя. Задайте получателя в настройках
карты. Пока поле пустое, накопленные уведомления остаются в очереди. Держите настройки SMTP
в закрытом файле окружения. В примере systemd это `/etc/netmap-pinger/netmap-pinger.env`.

### Выкладка фиксированного коммита

Для обновлений из Git держите в каталоге выкладки bare-репозиторий `repository.git`
с настроенным `origin`. Например, для доступного серверу репозитория используйте
`git clone --bare <url> /opt/netmap-pinger/repository.git`. Настройте службу на
`WorkingDirectory=/opt/netmap-pinger/current`, запретите запись байткода и держите
venv, базу и конфигурацию вне каталога релиза. Для первого запуска подготовьте эти
настройки до вызова скрипта. При переносе действующей службы сохраните старый unit
или drop-in, чтобы вернуть его при неудачном первом запуске.

На Debian запустите скрипт из проверенного коммита с Python 3.12 или новее.

```sh
sudo python3 netmap/deploy/release.py <full-sha> \
  --host netmap.example.org --backup-dir /var/lib/netmap-pinger/deploy-backups
```

Скрипт проверяет происхождение коммита из `origin/main`, сверяет файлы релиза с Git,
сохраняет копию SQLite и переключает `current` на каталог коммита. Если служба не
завершит первый цикл опроса или отдаст страницу из другого релиза, скрипт вернёт
предыдущий релиз. После выкладки проверьте HTTPS и доступ к карте через прокси.

## Проверки

Установите зависимости из `requirements-dev.txt` и выполните из корня репозитория:

```text
python -m pytest --durations=5
python -m netmap.app --help
python -m netmap.import_friendly --help
```

Браузерные проверки запускаются командой `node tests/layout.browser.cjs` с установленными
Playwright, Chromium, Firefox и WebKit. После пути к скрипту можно передать путь к модулю
Playwright и список браузеров через запятую. Тесты подменяют API и охватывают редактирование,
импорт JSON, статистику и сенсорные жесты. Скриншоты сохраняются только при заданной
`NETMAP_BROWSER_OUTPUT_DIR`.
